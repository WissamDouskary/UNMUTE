# Performance baseline — 19 October 2026

These are single-run, in-process timings on this Windows machine (AMD Ryzen 5 5600, 32 GB RAM). They are not HTTP timings, not PostgreSQL timings, and not canvas frame times. Repeat them with the commands below and replace the numbers. Do not treat them as a service-level target.

## Commands

```powershell
cd backend
.\mvnw.cmd "-Dtest=BaselineTimingTest" test
cd ..
npm run test -w apps/web
```

The Java lines are printed as `BRIEFING_RANK_2000_MS` and `GRAPH_SERVICE_1000_MS`. The Vitest lines are `GRAPH_<n>_MS` and `INBOX_2000_MS`.

## Results from this run

| Work | Dataset | Time |
| --- | --- | --- |
| `BriefingRank.rankOpenTasks` | 2,000 open tasks | 8 ms |
| `GraphService.getTopology` | 1,000 notes and 1,000 tasks, no SQL | 11 ms (2,000 nodes, 1,000 edges) |
| `filterGraph` + `neighborhood` + `buildInsights` | 100 notes | 1.5 ms (150 nodes, 81 insights) |
| same | 500 notes | 3.5 ms (750 nodes, 401 insights) |
| same | 1,000 notes | 12.5 ms (1,500 nodes, 801 insights) |
| same | 5,000 notes | 469.2 ms (7,500 nodes, 4,001 insights) |
| `inboxPhase` | 2,000 source statuses | 0.4 ms |

The graph page still asks the API for the whole topology and filters it in the browser. The 5,000-note figure is the cost of that preparation, not the cost of painting the force-directed canvas.

## Not measured

- `GET /api/v1/briefing` over HTTP.
- Inbox retrieval from PostgreSQL (`GET /api/v1/sources`).
- Graph SQL and the force-directed canvas at hundreds or thousands of nodes.
- Any run against the disposable database on port 5433.
